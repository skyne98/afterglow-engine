# Native Workers

A native worker is a real OS thread talking to its caller over heap-backed
rings. It's the fastest transport, and the one you use on the CEF desktop shell
when you want compute off the JS thread entirely.

## Spawning and calling one

```rust
use afterglow_rpc_demo::{Physics, PhysicsWorker, PhysicsServer, PhysicsClient};

let (client, events) = PhysicsClient::spawn_worker(PhysicsWorker)?;

let next = client.step(vec![0.0, 1.0, 2.0], 0.5)?;   // → [0.5, 1.5, 2.5]
assert!(client.apply_force(3, 0.0, 9.8, 0.0)?);
```

`spawn_worker` (generated by `#[rpc(worker = ...)]`) returns a typed
`PhysicsClient<WorkerTransport>` and an `EventReceiver`. Dropping the client
writes a shutdown frame, wakes the worker, waits up to 2 s, and joins the
thread.

## Starting it under CEF

`spawn_worker` creates an OS thread, and **spawning threads before CEF's
`execute_process` crashes the GPU process**. So spawn only from
`AppBuilder::on_ready`:

```rust
AppBuilder::new()
    .on_ready(|| {
        let (client, _events) = PhysicsClient::spawn_worker(PhysicsWorker).unwrap();
        // store `client` somewhere reachable, then return (don't block the UI thread)
    })
    .run();
```

`on_ready` fires exactly once, from the browser-process UI thread, after
`execute_process` and CEF init. Spawn the worker, hand it off, and return — the
worker runs on its own thread. See [The AppBuilder API](../window/app-builder.md).

If you don't need a native worker, leave `on_ready` unset and use the
page-driven `SharedArrayBuffer` transport instead (the `minimal` example does
this) — see [Web Workers](./web-workers.md).

## Events

Native workers have a third SPSC ring — the **event ring** — for fire-and-forget
messages from worker to page:

```rust
// From inside a worker method (native only):
afterglow_rpc::native::push_event(b"stepped:3")?;

// On the caller side:
let mut evs = Vec::new();
events.drain_into(&mut evs);
assert!(evs.iter().any(|e| e == b"stepped:3"));
```

- `push_event(bytes)` is called from the current native worker thread. Outside a
  worker loop it's a no-op; a full event ring returns `BufferFull`.
- `EventReceiver` has `try_recv()`, `has_data()`, and `drain_into(&mut out)`.

> **Events are native-only.** The web transport has request and response rings
> only — see [Lifecycle & Errors](./lifecycle.md).

## Allocation regression tests

Native executables can wrap `System` with
`afterglow_rpc::allocation::TrackingAllocator` and use `assert_no_alloc` in
sealed hot-path tests. Tracking is thread-local and opt-in. After ring storage
is constructed, `RingBuffer::write` plus `read_into` is covered by a zero-
allocation regression test.

## Singleton workers

For workers that are inherently global (an asset loader, an audio mixer), use
`#[rpc(worker = Type, singleton)]`. The first `spawn_worker` creates the worker;
subsequent calls return a clone sharing the same thread + rings. The client is
`Clone`.

```rust
#[rpc(worker = AssetLoaderWorker, singleton)]
pub trait AssetLoader {
    async fn load(path: String) -> RpcResult<Vec<u8>>;
}

// Set the root once, then spawn — returns the client directly.
AssetLoaderWorker::set_asset_root(AssetRoot::new("assets")?);
let client = AssetLoaderClient::spawn_worker()?;

// Other threads: clone the client (same worker, thread-safe).
let client2 = client.clone();
```

### Thread safety

The ring buffer is SPSC, but a singleton shared across N threads means N
producers. `AsyncWorkerTransport` wraps the ring halves in `Mutex`es,
serializing writes at the mutex level (microsecond holds — never during an
`await`). Multiple threads can call `call_async` / `poll` concurrently.

See [Defining a Service](./defining-a-service.md) for the `singleton` flag
and [The Asset System](../window/asset-system.md) for the asset loader.

## The raw ring primitive

Underneath the generated client, `afterglow_rpc::native` exposes the owned ring
halves directly, for ad-hoc use:

```rust
use afterglow_rpc::native::RingStorage;

let storage = RingStorage::new(1 << 20)?;       // 1 MiB
let (producer, consumer) = storage.split();

producer.write(b"request")?;
assert!(consumer.has_data());
let response = consumer.read()?;                 // allocates Vec<u8>
let n = consumer.read_into(&mut scratch)?;      // allocation-free
```

`RingStorage` owns one compact, 4-byte-aligned heap allocation containing the
header and byte data, shared internally with `Arc`. Consuming `split` creates
exactly one `RingProducer` and one `RingConsumer`; each half is `Send + !Sync`.

Public half methods:

```rust
RingProducer::{write, capacity}
RingConsumer::{read, read_into, peek_len, has_data, capacity}
```

`read_into` returns `BufferTooSmall` *without* consuming the frame, allowing a
retry with a larger destination.
