# Defining a Service

A worker service is a plain Rust trait annotated with `#[rpc]`. The macro
generates the server trait, the typed Rust client, and (with `worker = Type`)
the native spawn constructor, the wasm exports, **and a typed TypeScript
client** — all from the one declaration.

## The shape

```rust
use afterglow_rpc_macros::rpc;

#[rpc(worker = PhysicsWorker)]
pub trait Physics {
    fn step(state: Vec<f32>, dt: f32) -> Vec<f32>;
    fn apply_force(body_id: u32, fx: f32, fy: f32, fz: f32) -> bool;
}
```

The attribute is either empty (`#[rpc]`), `#[rpc(worker = Type)]`, or
`#[rpc(worker = Type, singleton)]`, where `Type` is the concrete server-impl
type. Method declarations must be plain `fn name(ident: Type, ...) -> Type;` —
the macro injects `&mut self` into the generated `<Name>Server` methods and
preserves the trait's visibility.

## The generated surface

For a trait `Physics` with `n` methods declared in order:

### `<Name>Server` trait

```rust
pub trait PhysicsServer {
    fn step(&mut self, state: Vec<f32>, dt: f32) -> Vec<f32>;
    fn apply_force(&mut self, body_id: u32, fx: f32, fy: f32, fz: f32) -> bool;
    /// Dispatch a (method, args) request. Provided.
    fn serve(&mut self, method: u32, args: &[u8]) -> RpcResult<Vec<u8>> { .. }
}
```

Method ids are `0, 1, …` in declaration order; `serve` matches on the id and
returns `RpcError::UnknownMethod` for any other id. You implement the
per-method `&mut self` functions; `serve` is provided.

### `<Name>Client<T: Transport>`

```rust
pub struct PhysicsClient<T: Transport> { /* private transport */ }
impl<T: Transport> PhysicsClient<T> {
    pub fn new(t: T) -> Self;
    pub fn transport(&self) -> &T;
    pub fn step(&self, state: Vec<f32>, dt: f32) -> RpcResult<Vec<f32>>;
    pub fn apply_force(&self, body_id: u32, fx: f32, fy: f32, fz: f32) -> RpcResult<bool>;
}
```

Each method encodes its args as a postcard tuple (`(arg0, arg1, …)`), calls
`Transport::call(method_id, &args)`, and decodes the returned payload. Trailing
commas force tuple semantics, so a single-argument method round-trips the same
way as a multi-argument one. Fields stay private; use `transport()` for ad-hoc
raw calls.

### Native spawn (only with `worker = Type`)

```rust
#[cfg(not(target_arch = "wasm32"))]
impl PhysicsClient<WorkerTransport> {
    pub fn spawn_worker(impl_: PhysicsWorker) -> RpcResult<(Self, EventReceiver)>;
}
```

Spawns the worker on an OS thread over 1 MiB request/response/event rings and
returns the typed client + event receiver. The worker thread is joined when
the client is dropped. See [Native Workers](./native-workers.md).

### Wasm exports (only with `worker = Type`)

```text
afterglow_wasm_init() -> void
afterglow_wasm_serve_frame(method, args_ptr, args_len, out_ptr, out_max) -> i32
afterglow_wasm_input_ptr() -> usize
afterglow_wasm_input_size() -> usize   # 1 MiB
afterglow_wasm_output_ptr() -> usize
afterglow_wasm_output_size() -> usize  # 1 MiB
```

`afterglow_wasm_init` constructs `Type::default()`, so the worker type **must
implement `Default`**. See [Web Workers](./web-workers.md).

### TypeScript client (only with `worker = Type`)

The macro also generates a typed `.ts` client at
`<crate>/ts/<name>.client.ts`. It wraps the low-level byte `rpc.call(methodId,
args)` with typed async methods and postcard codecs for the **specific types on
the trait** — not arbitrary serde. For the `Physics` trait above:

```ts
// AUTO-GENERATED by #[rpc]. Do not edit.
import { RpcTransport, concat, decodeBool, decodeF32Vec,
         encodeF32, encodeF32Vec, encodeU32 } from './codec.js';

export class PhysicsClient {
  constructor(private rpc: RpcTransport) {}

  async step(state: Float32Array, dt: number): Promise<Float32Array> {
    const args = concat(encodeF32Vec(state), encodeF32(dt));
    const resp = await this.rpc.call(0, args);
    return decodeF32Vec(resp, 0)[0];
  }

  async applyForce(bodyId: number, fx: number, fy: number, fz: number): Promise<boolean> {
    const args = concat(encodeU32(bodyId), encodeF32(fx), encodeF32(fy), encodeF32(fz));
    const resp = await this.rpc.call(1, args);
    return decodeBool(resp, 0)[0];
  }
}
```

`cargo run -p xtask wasm` copies generated `.ts` clients into
`crates/afterglow-web/www/` alongside `codec.ts` (the postcard codec library).

**Supported types** (rejected at compile time with a clear error otherwise):

| Rust | TypeScript |
|---|---|
| `f32`, `f64` | `number` |
| `u8`, `u16`, `u32`, `u64`, `usize` | `number` |
| `i8`, `i16`, `i32`, `i64`, `isize` | `number` |
| `bool` | `boolean` |
| `String` | `string` |
| `Vec<u8>` | `Uint8Array` |
| `Vec<f32>` | `Float32Array` |
| `Vec<f64>` | `Float64Array` |
| `()` | `void` |

Rust `snake_case` method names become TS `camelCase` (`apply_force` →
`applyForce`). See [Web Workers](./web-workers.md) for how to use the generated
client from the page.

## The `singleton` flag

`#[rpc(worker = Type, singleton)]` makes the worker a **process-global singleton**.
The first `spawn_worker` call creates the worker; subsequent calls return a
**clone** of the client sharing the same underlying worker thread and rings.

```rust
#[rpc(worker = AssetLoaderWorker, singleton)]
pub trait AssetLoader {
    async fn load(path: String) -> RpcResult<Vec<u8>>;
}

// First call: spawns the worker thread (constructs the impl via Default).
let client = AssetLoaderClient::spawn_worker()?;

// Second call: returns a clone — same worker, same rings.
let client2 = AssetLoaderClient::spawn_worker()?;

// `client.clone()` also shares the same worker.
let client3 = client.clone();
```

### What changes

| | Per-spawn (default) | Singleton |
|---|---|---|
| `spawn_worker` returns | `(Self, EventReceiver)` | `Self` (no args — constructs via `Default`) |
| Client is `Clone` | no | yes (`Arc` clone) |
| Multiple `spawn_worker` calls | each spawns a new worker thread | first wins; later calls clone the `Arc` |
| Thread safety | SPSC, one caller | `Mutex`-protected rings, N callers |

### Why `Mutex`-protected rings?

The ring buffer is SPSC (single-producer, single-consumer). A per-spawn worker
has one caller writing the request ring — that's fine. But a singleton shared
across N threads means N producers writing the request ring concurrently. The
`AsyncWorkerTransport` wraps the ring halves in `Mutex`es, serializing writes at
the mutex level (microsecond-level holds — never during an `await`).

### When to use it

Use `singleton` for workers that are inherently global — an asset loader, an
audio mixer, a save manager. Use per-spawn (the default) for workers that are
ephemeral or per-session — a physics sim per level, an AI per entity.

## Sync vs async `#[rpc]`

The macro detects `async fn` and generates the async code path automatically.
A trait is all-sync or all-async — mixed is not supported.

| | Sync `#[rpc]` | Async `#[rpc]` |
|---|---|---|
| Methods | `fn name(args) -> T` | `async fn name(args) -> RpcResult<T>` |
| Server receiver | `&mut self` | `&self` (interior mutability) |
| Client call | blocks (parks) until response | returns a `Future` immediately |
| In-flight calls | one at a time (SPSC) | multiple (task_id matching) |
| Client API | `client.step(...)` → `RpcResult<T>` | `client.load(...)` → `RpcResult<impl Future>` + `poll()` |
| Worker loop | `run_worker_loop` | `run_async_worker_loop` (with `LocalExecutor`) |
| Framing | `[method][args]` | `[method][task_id][args]` / `[task_id][Response]` |
| Events | event ring (native) | response ring carries completions |
| `singleton` flag | not supported (sync is per-spawn) | supported (Mutex-protected rings, `Clone` client) |

### The poll model (async)

Async `#[rpc]` uses a **pull-based** completion model — the worker never wakes
the client; the client pulls each frame:

- **`call_async(method, args)`** (under the hood of every generated async method)
  mints a `task_id`, writes `[method][task_id][args]` to the request ring,
  registers `task_id → resolver` in a `HashMap`, and returns a `Future`.
  **Never blocks.**
- **`poll()`** drains the response ring: each completion is
  `[task_id][Response]`. It matches `task_id`s and resolves the corresponding
  futures.
- Multiple in-flight calls are supported (each gets a unique `task_id`).
- The worker runs an `async-executor::LocalExecutor`; `poll()` also ticks the
  executor, so the frame rate drives task progress.

On the TS side, the generated `spawn()` + `poll()` on the client hides this —
you just `await` the method call, and it resolves on a later `poll()`.

## Implementing the server

The concrete impl is a normal struct that implements the generated server trait:

```rust
#[derive(Default)]
pub struct PhysicsWorker;

impl PhysicsServer for PhysicsWorker {
    fn step(&mut self, mut state: Vec<f32>, dt: f32) -> Vec<f32> {
        for v in state.iter_mut() { *v += dt; }
        state
    }
    fn apply_force(&mut self, body_id: u32, fx: f32, fy: f32, fz: f32) -> bool {
        body_id % 2 == 1 && (fx + fy + fz).abs() > 0.0
    }
}
```

`#[derive(Default)]` is required for the wasm path (`afterglow_wasm_init`
constructs `Type::default()`).

## The codec: postcard

Arguments and results are serialized with [postcard]. A method call's request
payload is `[method_id: u32 LE][postcard args]`, where `args` is the method's
arguments encoded as a tuple. Every server reply is postcard-encoded as one of:

[postcard]: https://docs.rs/postcard

```rust
enum Response {
    Ok(Vec<u8>),                 // success — the postcard-encoded result
    Server { method, message },  // the server method returned Err
    Decode { method, message },  // the server couldn't decode the args
}
```

This envelope is what lets a successful zero-byte/unit return (e.g.
`fn log(msg: String)`) be distinguished from an error.

## What the macro rejects (at compile time)

A `syn::Error`, never a panic, for any of:

- a `self` / `&self` / `&mut self` receiver;
- trait generics, a `where` clause, or any supertraits;
- `const`, `unsafe`, `extern`, or variadic (`...`) methods;
- generic methods, or methods with a `where` clause;
- associated consts or types, or methods with default bodies;
- non-identifier parameter patterns (e.g. `(x,): (u32,)`).

> **`async fn` is now allowed.** The macro detects `async fn` and generates
> the async code path (poll model). See [The Asset System](../window/asset-system.md)
> for the async transport details.

## Reserved method names

- `serve`, `new`, and `transport` are **always** reserved.
- `spawn_worker` is reserved **only when `worker = ...` is used**. Without
  `worker`, a method named `spawn_worker` is allowed.

## One worker service per wasm cdylib

The wasm exports use fixed `#[no_mangle]` names (`afterglow_wasm_*`), so **at
most one `#[rpc(worker = ...)]` service may be linked into a single wasm
cdylib**. Multiple *non-worker* `#[rpc]` traits (no `worker = …`) may coexist
in one module — they only generate `Server` / `Client` names and never emit wasm
symbols.
