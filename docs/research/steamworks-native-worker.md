# Steamworks via Native Rust Worker + Overlay

> Investigated 2026-07

## Overview

Steamworks (achievements, leaderboards, friends, overlay, multiplayer) is a
C/C++ SDK (`steam_api.so` / `steam_api64.lib`). It can't run in wasm — it
must be a **native worker**. On the web target, Steamworks isn't available
(web games use Steam's browser-based APIs instead).

The plan: expose Steamworks as a `#[rpc(worker = SteamWorker)]` native
worker, callable from the game loop via the ring buffer — same as any other
worker. The overlay is loaded automatically when `SteamAPI_Init()` is called
before GPU init.

## The `steamworks` Rust crate

[`steamworks`](https://crates.io/crates/steamworks) (by Noxime) provides
safe Rust bindings to the Steamworks SDK. It dynamically loads
`steam_api.so` / `steam_api64.lib`.

```toml
[dependencies]
steamworks = "0.12"
```

The SDK redistributables (`steam_api.so`, `steam_api64.dll`) must be in the
executable's directory or on the library search path.

### Key API

```rust
use steamworks::Client;

// 1. Init — calls SteamAPI_Init() internally.
//    MUST be called before the graphics device is created (for overlay).
let client = Client::init().unwrap();

// 2. Register callbacks (run on the thread that calls run_callbacks)
let _cb = client.register_callback(|v: steamworks::GameOverlayActivated| {
    if v.activated {
        // Pause the game — overlay is open
    } else {
        // Resume — overlay closed
    }
});

// 3. Call every frame (at least once per second)
client.run_callbacks();

// 4. API accessors
client.friends().request_user_information(steam_id, true);
client.user_stats().set_achievement("COMPLETE_LEVEL_1")?;
client.user_stats().store_stats()?;
client.utils().app_id();
client.matchmaking().request_lobby_list(|lobbies| { ... });
```

## Architecture for afterglow-engine

### Initialization order (critical)

```
main()
  ├─ steamworks::Client::init()     ← SteamAPI_Init() + overlay renderer loaded
  ├─ afterglow_cef::AppBuilder::run()
  │    ├─ CEF init (GPU process starts — overlay hooks vkQueuePresentKHR)
  │    └─ on_context_initialized()
  │         └─ spawn_worker(SteamWorker)  ← ring buffer worker
  └─ (CEF message loop runs)
```

**`SteamAPI_Init()` MUST be called before CEF init** — the overlay hooks
graphics device creation. If CEF's GPU process starts first, the overlay
can't hook it.

With `--in-process-gpu`, the GPU runs in the main process. The overlay
(hooked into the main process via `SteamAPI_Init`) can intercept
`vkQueuePresentKHR` / `Present`.

### The Steamworks worker

```rust
use afterglow_rpc_macros::rpc;
use steamworks::Client;

#[rpc(worker = SteamWorker)]
pub trait Steamworks {
    fn unlock_achievement(id: String) -> bool;
    fn get_achievement(id: String) -> bool;
    fn set_stat(name: String, value: f32) -> bool;
    fn get_leaderboard_score(name: String) -> i32;
    fn open_overlay(name: String) -> bool;
    fn is_overlay_active() -> bool;
}

pub struct SteamWorker {
    client: Client,
}

impl SteamWorker {
    fn new() -> Self {
        // Client was already init'd in main() — get a reference
        // steamworks::Client is Send + Sync (wraps thread-safe C API)
        // We need to pass the Client from main() to the worker.
        // Option 1: store in a static (like we did with MAIN_BROWSER)
        // Option 2: pass as argument to spawn_worker
        todo!()
    }
}

impl SteamworksServer for SteamWorker {
    fn unlock_achievement(&mut self, id: String) -> bool {
        self.client.user_stats().set_achievement(&id).is_ok()
    }

    fn is_overlay_active(&mut self) -> bool {
        self.client.utils().is_overlay_enabled()
    }

    // ... other methods
}
```

### RunCallbacks in the worker loop

The worker's `run_worker_loop` (generated by `#[rpc]`) spins reading from
the request ring buffer. Between requests, it should call
`client.run_callbacks()`:

```rust
// The worker loop (conceptual — would be integrated into run_worker_loop):
loop {
    // 1. Check for RPC requests
    match transport.request.read() {
        Ok(frame) => { /* call serve */ }
        Err(BufferEmpty) => {}
    }
    // 2. Pump Steam callbacks
    client.run_callbacks();
    // 3. Yield
    std::hint::spin_loop();
}
```

This ensures callbacks (like `GameOverlayActivated`) are dispatched promptly.
The callback can push an event to the main thread via the event channel
(`push_event`).

### Overlay events → game loop

When the overlay opens/closes, the `GameOverlayActivated` callback fires
(in the worker thread). The worker pushes an event to the main thread:

```rust
let _cb = client.register_callback(|v: steamworks::GameOverlayActivated| {
    afterglow_rpc::native::push_event(
        format!("overlay:{}", if v.activated { "open" } else { "closed" }).into_bytes()
    );
});
```

The game loop drains events each frame:
```rust
events.drain_into(&mut event_buffer);
for ev in &event_buffer {
    if ev.starts_with(b"overlay:open") {
        game.pause();
    } else if ev.starts_with(b"overlay:closed") {
        game.resume();
    }
}
```

### The `Client` lifetime problem

`steamworks::Client` is created by `Client::init()` (which calls
`SteamAPI_Init`). It must be created in `main()` before CEF init. But
`spawn_worker` takes ownership of the worker struct.

**Solution:** Store the `Client` in a `static` (like `MAIN_BROWSER`), or
wrap it in `Arc`:

```rust
// In main():
static STEAM: Mutex<Option<steamworks::Client>> = Mutex::new(None);
*STEAM.lock().unwrap() = Some(steamworks::Client::init().unwrap());

// In SteamWorker::new():
let client = STEAM.lock().unwrap().take().unwrap();
SteamWorker { client }
```

Or better: pass the `Client` directly to `spawn_worker`. The `Client` is
`Send + Sync`, so it can be moved into the worker thread.

```rust
// In main():
let client = steamworks::Client::init().unwrap();

// After CEF init (in on_context_initialized):
let (steam_client, steam_events) = spawn_worker(SteamWorker::new(client));
```

But `spawn_worker` is generated by the macro and called after CEF init.
The `Client` must survive from `main()` to `on_context_initialized()`.
Store it in a `static` or pass through `Config`.

## CEF flags for overlay

```rust
// In afterglow-cef/src/flags.rs:
sw(cl, "in-process-gpu");  // GPU in main process — overlay can hook it
```

Without `--in-process-gpu`, the GPU runs in a separate process. The overlay
(loaded into the main process by `SteamAPI_Init`) can't hook the GPU
process's rendering. See `docs/research/steam-overlay-cef.md` for details.

## `steam_appid.txt`

A file containing the Steam App ID (e.g., `480` for Spacewar), placed next
to the executable. Required for development/testing outside of Steam. When
launched via Steam, the app ID is passed automatically.

```
steam_appid.txt:
480
```

## What doesn't work on web

Steamworks SDK is native-only (`steam_api.so` / `steam_api64.dll`). On the
web target, Steamworks isn't available. Web games distributed via Steam use
Steam's browser-based features (Steam Cloud Web API, browser overlay in
Steam's built-in browser). The `#[rpc(worker = SteamWorker)]` macro
generates `spawn_worker` for native only — on web, the trait exists but
`spawn_worker` is not generated (`#[cfg(not(target_arch = "wasm32"))]`).

## Summary: what needs to be built

1. **Add `steamworks` dependency** to the game crate (not the engine crates)
2. **Call `Client::init()` in `main()`** before `AppBuilder::run()`
3. **Add `--in-process-gpu`** to CEF flags
4. **Write `#[rpc(worker = SteamWorker)] trait Steamworks`** with the methods
   the game needs (achievements, stats, overlay, friends)
5. **Implement `SteamworksServer`** wrapping the `steamworks::Client`
6. **Modify `run_worker_loop`** to call `client.run_callbacks()` between
   requests (or add a "tick" mechanism to the worker loop)
7. **Handle overlay events** via `push_event` → game loop drains
