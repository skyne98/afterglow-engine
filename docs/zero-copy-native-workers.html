Zero-copy native workers

The render (rusty_v8 JS) thread and worker OS threads share one address space and one wgpu-core device. So payloads never need to cross as bytes — they live in a shared arena (generational handles) or on the GPU itself (a shared resource table). The ring becomes a signalling channel for 12-byte handles, not a byte pipe.

This is a native-only capability. Web (wasm + SAB) keeps the byte path — separate memories make true zero-copy impossible there.

0Where copies happen today

The ring backing (Arc<RingAlloc>) is already shared memory. The API memcpy's through it and allocates a Vec per call. Texture pages cross as bytes.

1The zero-copy design — three primitives

Keep the byte ring + postcard for small control (method id + scalars, 2.4 µs at 64 B). Move large payloads out of the ring into a shared arena or the GPU itself.

zero-copy (in-place) 12-byte handle over ring GPU path (no bytes to JS) worker↔worker direct

① Shared payload arena — generational handles

A Rust-owned fixed-capacity arena (the native realization of EngineMemory), Arc'd. Both JS (v8 ArrayBuffer view) and workers (raw ptr) read/write the same slots. The ring carries a handle, not the payload.

② Shared GPU resource table — texture pages never become JS bytes

Workers obtain a wgpu::Device/Queue from the shared Arc<wgpu_core::global::Global> (same pattern the HUD presenter already uses) and call queue.writeTexture directly. They return a generational texture handle; the renderer binds it. Zero bytes cross to JS.

③ Worker ↔ worker — direct, no renderer hop

Two workers exchanging data (asset loader → texture, physics → audio) share an arena + a lock-free SPSC handle queue. Direct Rust-to-Rust, same address space. No JS round-trip, no byte copy.

2Mapping to the web comms we already have

The web Rpc.call(method, args) already returns a view over the SAB (new Uint8Array(this.mem.buffer, this.scratch, n)) — the SAB is the shared memory, views are zero-allocation, and postMessage carries no payload (wakeups only; the ring is the transport). The native design is the same abstraction with a different backing store.

What is identical across targets

The call(m, args) → view API

Same RpcTransport interface the generated TS clients take. Both return Uint8Array views over shared memory — SAB on web, arena on native. Game/demo code and the generated clients are byte-identical across targets.

Codec + method IDs + wakeups-only

Postcard framing and method IDs are shared. Both transports wake the other side with a payload-free signal (postMessage on web, unpark on native) — the shared memory is the transport, exactly as today.

The handle is not a new wire format — it's a 12-byte postcard value passed through the same call() the web path uses. Web just never produces one (it passes bytes); native produces one because the arena is shared. Same codec, same clients, same method signatures.

3What stays the same

Byte ring + postcard = control

Method id + small scalars + a handle. 2.4 µs at 64 B. Copying 12 bytes is negligible. The ring is a signalling channel, not a payload pipe — on both targets.

Generated TS clients unchanged

The codec + method IDs are identical. Bulk methods take/return handle-typed args on native, byte-typed on web — both are normal postcard values through the same call().

D1 Arena ownership: one engine-wide EngineMemory vs per-worker-pair arenas One engine-wide arena (matches AGENTS.md "single logical EngineMemory")
D2 Transport::call -> Vec<u8> allocates per call — kill it? Keep for control; add handle-typed args + out-buffer path for bulk
D3 Shared GPU resource table — workers call the shared Global from their threads Yes — biggest win (texture pages stop crossing to JS)
D4 Web target — zero-copy is native-only Native gets arena + GPU table; web keeps byte path. Don't compromise native for web
D5 Worker↔worker: dedicated HandleQueue vs reusing the byte ring Dedicated HandleQueue<S,G> — cleaner, skips renderer entirely
Proof order. Start with D3 — wire the texture worker to upload to the shared Global and return a texture handle the renderer binds. That's the single highest-impact zero-copy win and validates "shared Global from a worker thread" before building the arena (D1/D2) and the worker↔worker queue (D5).
